## Что уже исправил #128

Periodic unique work зарегистрирован с UPDATE, one-off при open/resume — с KEEP.
Оба требуют connected network и battery-not-low. Open/resume независимо запускает
асинхронный foreground catch-up; UI, Firebase и native registration его не блокируют.
Успешный manual checkpoint откладывает пару на 30 минут, ошибка — на 5 минут,
не сокращая уже действующий успешный интервал. Эти изменения сохранены.

## Полный путь и прерывания

`chapterWorkDispatcher` → `ChapterScanRunner.run` → `ChapterChecker._scheduled`
→ SQLite claim пары книга/источник → detail → canonical/source-seen/read/inbox
решения → pages (валидный HTTPS URL, без обхода доступа) → durable inbox insert
→ read reconciliation → seen checkpoint → queue finish.

Inbox v4, уникальные идентичности, hidden state, OS delivery lease/fencing и
read-vs-inbox защита #125 сохранены. Найденная глава checkpoint-ится отдельно;
повтор после аварии использует уже существующую запись, включая скрытую.
Прогресс чтения, SharedPreferences blob библиотеки, read markers и перевод не
переписываются сканером. Профиль захватывается до проверки, затем перепроверяется
при сохранении и по окончании. Provider cooldown общий на устройстве, inbox и
результаты запусков раздельны для гостя и каждого UID.

120 секунд на запуск и 45 секунд на пару остаются. `Future.timeout` не отменяет
transport: после timeout lease пары остаётся конечным (5 минут), а закрытый
deadline zone не позволяет позднему ответу записать inbox/seen. Следующий запуск
обрабатывает другие книги и возвращается к прерванной паре после lease. Отдельные
ошибки не стирают уже сохранённые главы. Успешные пары ждут 30 минут; ошибки —
5 минут; 403/429 и Retry-After имеют приоритет над этим интервалом.

Время проверки и rate limits Senkuro/ReadManga не ускоряются. Существующие
двухсекундные provider gaps, HTTP timeouts и запреты источников сохранены.
Полная загрузка большого Senkuro detail включает pagination и может не уложиться
в 45 секунд; теперь такой случай виден как timeout, не success. Изменений адаптера
или увеличения бюджета без измерений нет.

OS delivery идёт после обязательного inbox. Она читает только pending intents
ограниченной партией из v4, не переустанавливает discoveries. Запрет Android
permission/ошибка plugin не меняет результат discovery. Pending intent сохраняется,
его последующая отправка использует прежние stable notification IDs и fencing.

## Диагностика

Отдельно показаны последние open/resume и WorkManager: начало, подтверждённый
конец, длительность, последний checkpoint, доступные пары книга × источник,
обработанные/успешные/ошибочные/оставшиеся пары, найденные главы, причины ожидания
и nextEligibleAt. Последний показатель — нижняя граница, не обещание запуска Android.
Счётчики решений по главам объясняют silent baseline, source-seen, read, inbox
duplicate, нераспознанные метаданные и недоступные страницы. OS delivery имеет
отдельный статус; регистрация Android не выдаётся за фактический запуск.

Каждый запуск получает монотонный ID. В SQLite хранится восемь новых диагностических
попыток на origin/профиль. Ротируется только эта новая служебная история; имеющиеся
библиотека, inbox, jobs/providers и старые summary не удаляются. Общие ошибки
bootstrap best effort сохраняются в profile/origin-scoped SharedPreferences,
если SQLite недоступна, но preferences работают. Тексты исключений, книги, URL и
токены в диагностику не записываются.

Checkpoint продлевает срок подтверждения активности на 3 минуты (больше обычного
scan budget). В течение этого срока run отображается «Выполняется», в том числе
в минуту начала с нулевыми счётчиками. После срока — «Завершение не подтверждено;
срок активности истёк». Это консервативный признак прерывания/задержки, не доказательство
убийства процесса Android. Поздний running/success от истёкшего владельца не стирает
сохранённый снимок. Новый процесс может не сразу отличить ещё живой другой isolate;
он соблюдает lease вместо ложного мгновенного объявления зависания.

Очередь SQLite обновляется v1→v2 только добавлением таблицы/index диагностики.
Миграция тестируется с прежними jobs, token, lease, source ID и cooldown.
Inbox остаётся v4. Старые summary читаются без придуманного времени завершения.

## Что намеренно не выдаётся за исправленное

Первая успешная проверка источника сохраняет исходный список тихо. Исключение —
прежняя политика recent unread после последней прочитанной главы (36 часов,
до двух подтверждений за baseline); отложенные кандидаты остаются unseen и
проверяются даже после этого окна. Если данных для отличия старого каталога от
новой публикации нет (первый scan, нет read anchor/даты), всю историю не рассылаем.
Уже проглоченные legacy seen-главы старше recovery window невозможно безопасно
массово восстановить без повторной рассылки старых выпусков. Нераспознанные
ненумерованные главы учитываются диагностикой; ключи из названий не выдумываются.

70–200 книг с двумя источниками могут требовать нескольких запусков. Doze,
энергосбережение, offline, battery-not-low и force-stop допускают большие задержки;
точных 15 минут нет. При открытии сразу виден сохранённый inbox, неизвестные ещё
обновления появятся после async catch-up. Force-stop проверяется отдельно:
Android обычно не выполняет work до ручного открытия.

## Проверка на Pixel после ревью PR

1. Обновить с сохранением данных/подписи, не удалять приложение. Сравнить страницу,
   read markers, активный перевод, гостя/UID до и после.
2. Открыть настройки в ту же минуту начала: running с нулём допустим; спустя
   несколько минут получить конец либо истёкший срок активности, отдельно по origin.
3. Запустить foreground catch-up одновременно с native work; сверить counts,
   lease/interval/cooldown и отсутствие дублей/перезаписи отчётов.
4. После нескольких checkpoint остановить процесс, восстановить сеть, перезагрузить
   телефон; открыть inbox, дождаться освобождения lease и следующей попытки.
5. Выключить POST_NOTIFICATIONS: внутренние обновления должны появляться; проверить
   partial burst, архив, retry CDN и последующий OS drain без старой массовой рассылки.
6. Сохранить ограниченные logcat/JobScheduler данные с датой и версией APK, режимом
   батареи и сетью. Не публиковать UID/URL/библиотеку. Принудительный job через ADB
   не доказывает штатный периодический запуск. Реальные 429 специально не провоцировать.

Flutter/SQLite тесты моделируют сбои и конкуренцию; они не заменяют Android
JobScheduler/Doze на устройстве. APK не публикуется, PR не объединяется автоматически.
