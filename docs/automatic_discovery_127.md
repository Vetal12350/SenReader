# Диагностика автоматического поиска (#127)

База: main `92ad355`, Issue #127 прочитан вместе с доступными комментариями
(на момент исследования комментариев не было). Физического Pixel/ADB здесь нет.
Сообщение пользователя воспроизвести именно на его устройстве пока невозможно;
ни Doze, ни батарея не объявляются установленной причиной.

## Три разных сценария

| Сценарий | Подтверждённое поведение / вывод |
| --- | --- |
| WorkManager не начал задачу | Periodic: одно unique work, 15 минут, connected + battery-not-low, policy UPDATE. One-off: unique KEEP с теми же constraints при open/resume. Регистрация не доказывает запуск. Раньше catch-up тоже зависел от WorkManager, а cold start ожидал завершения notification plugin и Firebase. Зависание этих зависимостей могло лишить приложение восстановления при открытии. Catch-up теперь запускает ограниченную async-проверку независимо от native registration/Firebase; UI её не ожидает. Periodic и one-off остаются для закрытого приложения. |
| Задача началась, но не выбрала пары | Подтверждены тестами две несогласованности ручного расписания и SQLite: успешная ручная проверка не откладывала уже существующее задание; неудачная ручная проверка при создании очереди откладывала его на 30 минут вместо 5. Теперь попытки сразу checkpoint-ятся в очередь; успех откладывает на 30 минут, ошибка на 5, без сокращения уже действующего успешного интервала и без отъёма lease/token. HTTP 403/429, их cooldown и provider gates сохранены. |
| Найдено, но нет во внутренней ленте | В пределах проверенных сценариев новый дефект не подтверждён. Inbox-before-seen, read reconciliation, UID, дедупликация и SQLite v4 из #125 сохранены. Новые проверки проходят через тот же checker. OS permission/plugin не участвует в обязательной записи inbox. Повторная передача discoveries из worker в notification service больше не требуется: service получает пустой отчёт и читает только pending OS intent из v4. |

На исходном коде два новых регрессионных теста дали **296 passed, 2 failed**:
[первый CI](https://github.com/Vetal12350/SenReader/actions/runs/41529961379).
Первый получил checked=1 вместо 0, второй — 0 вместо 1.
Это подтверждённые дефекты кода, но не доказательство причины всего дня пропусков
на Pixel: неудачная ручная попытка сама по себе объясняет лишь ограниченную паузу.

## Сохранение и наблюдаемость

В profile-scoped SharedPreferences записываются начало, checkpoints завершённых
пар и итог автоматического запуска. Только фиксированные коды: running, success,
partial, skipped, error; время начала, origin, checked/skipped/found, warnings,
причина и нижняя граница nextEligibleAt. Не сохраняются названия книг, URL,
сообщения исключений или токены. Последний WorkManager хранится отдельно от
последнего catch-up, регистрация задач — отдельно от фактической проверки.
Старые summary читаются без изменения данных библиотеки.

Если процесс погиб, остаётся «Начата; завершение не подтверждено» и счётчики
последнего завершённого checkpoint. Это может также означать ещё работающий scan;
по одному флагу нельзя утверждать, что процесс был убит. Ошибки bootstrap плагинов
пишутся best effort: если не работает сам storage plugin, запись невозможна.
Отказ отдельного источника отмечается partial с безопасной причиной HTTP/timeout/
network-or-source; полное исключение runner отмечается error. Отложенный scan с
нулём запросов не выдаётся за успешную проверку всех книг. Ошибка OS notification
не меняет успешный результат discovery; retry intent/lease/fencing остаются в v4.

Бюджет 120 секунд, slice пары 45 секунд, постоянная очередь и исходные ограничения
провайдеров сохранены. Проверка при открытии использует те же claims/gates, даже
если одновременно работает WorkManager. Статусы, идентичность источников,
прочитанные главы и страницы не меняются. Исторические ручные timestamps могут
сохранить старую паузу до её естественного истечения; массовой миграции/reset нет.

Внутренняя лента сразу показывает уже сохранённые обновления. Новые главы,
которые никто ещё не обнаружил, появятся после неблокирующего catch-up/следующей
задачи. Для 70–200 книг с двумя источниками нужны несколько сетевых запусков:
не обещаем обработать всё за 2 минуты. Ошибка/таймаут не переключает перевод.
Первый scan по-прежнему формирует тихую baseline с существующим исключением для
подтверждённых недавних непрочитанных глав; это не изменённая политика уведомлений.

Doze, battery saver, отсутствие сети, ограничения фоновой активности и force-stop
могут отложить/остановить native work. UPDATE восстанавливает periodic registration,
KEEP не создаёт множество одинаковых one-off задач. 15 минут — не точный таймер.
Открытие приложения обеспечивает независимую попытку; незавершённые пары после
гибели процесса остаются под конечным lease и доступны позже. Очень медленная
загрузка detail может по-прежнему превышать slice: диагностика покажет timeout,
а очередь сохранит задание. CAPTCHA/HTTP 403/429 не обходятся.

## Проверка на Pixel 8 Pro перед объединением

1. Не переустанавливать с удалением данных. Сохранить скрин настроек: оба
   переключателя, последняя попытка, последняя задача WorkManager, регистрация.
   Записать версию Android, заряд, сеть, battery saver и режим батареи приложения.
2. Выключить системные уведомления/POST_NOTIFICATIONS, включить внутренний поиск.
   Открыть приложение: сначала виден существующий inbox, затем origin «при
   открытии» и итог. Проверить новые главы, архив, два UID/гостя, страницу чтения.
3. После истечения 30 минут оставить приложение в фоне, затем с выключенным
   экраном/Doze; сверить отдельную дату WorkManager. При разрешённой ADB-отладке
   сохранить `adb shell dumpsys jobscheduler` и logcat по WorkManager/flutter
   (без публикации UID, библиотеки, URL/токенов). Искусственно принудительный job
   не доказывает штатный periodic запуск.
4. Проверить отсутствие сети и low battery: отсутствие запуска под constraints
   ожидаемо; после возвращения сети/открытия должна появиться новая попытка.
   При source cooldown нет запросов к запрещённому провайдеру, другой продолжает.
   Не генерировать реальные 429 специально: имитировать отказ в тестовом transport.
5. Убить процесс во время нескольких завершённых пар, перезагрузить телефон;
   убедиться в сохранности inbox, finite lease, продолжении остальных книг и
   отсутствии дублей. Проверить force-stop отдельно: Android не обязан запускать
   задачи до ручного открытия. После открытия catch-up должен восстановиться.
6. Для 70–200 книг сравнить checked/skipped нескольких запусков и timestamps
   источников: равноправная очередь, без лимита 12 и без массового HTTP burst.
   На медленной сети проверить, не повторяется ли timeout одной и той же пары.

Настройки не являются трассировкой Android JobScheduler: окончательная причина
отсутствия native запуска на конкретном телефоне требует журналов устройства.
