## Путь изображения и проверка десяти гипотез

`loadChapterPagesWithRetry(source, chapter)` получает URL/headers выбранного
источника. Reader строит ленивый `ScrollablePositionedList`. Видимые страницы
и speculative probes разрешают один и тот же `ResizeImage(NetworkImage)`
с одинаковыми URL, headers и decode width. `NetworkImage` собирает HTTP body
в байты, создаёт `ImmutableBuffer`, вызывает codec; `getNextFrame` асинхронно
возвращает кадр. Flutter ImageCache хранит pending/completed/live состояния;
`Image` подписывается на stream, `RawImage` участвует в layout/paint, затем
engine/raster выполняет подготовку/использование текстур и подаёт кадр.

**Файлового кеша изображений в production-коде нет.** Наличие файлов в стенде,
кеш источника со списками/карточками и декодированный Flutter ImageCache —
разные вещи. После потери bitmap может понадобиться новый HTTP-запрос.

|---|---|

## Единственное оставленное архитектурное изменение

`_updatePixelWindow` сразу активирует видимые страницы и уже допущенных
соседей. Новый невидимый кандидат получает pixels только после занятия
слота в `_pumpGeometry`. Поэтому первоначальная подготовка нового невидимого
кандидата не обходит concurrency, cooldown, проверку известного большого bitmap
и слоты устаревших запросов. Отдельные retry/resize уже активного Image не
становятся глобальной очередью decode этим изменением. Первичная
активация больше не включает безусловно следующую страницу. Режим по высоте
теперь тоже использует очередь, без публикации ненужной геометрии.

Приоритеты и размеры окна прежние. Видимая страница не ждёт speculative
очередь и использует тот же pending/decoded stream, если он есть в ImageCache.
Формат данных, сохранение позиции/read markers, источник, параметры decode,
качество/фильтрация, рисование стыков и package основного приложения не менялись.

Новый управляемый тест оставляет прежние HTTP/decode незавершёнными, быстро
перемещает viewport и проверяет реальные новые загрузки вне видимости.
На прежнем коде появляются лишние страницы 7, 8 и 4; с исправлением — ни одной.
Проверены режимы по ширине и по высоте. Это доказательство соблюдения очереди,
не измерение FPS на телефоне.

Эксперимент с отпиской probe в конце кадра откатан. Как показывает отдельный
синтетический случай без keepAlive, этого недостаточно, чтобы гарантировать
отсутствие повторного decode при более позднем создании tile. Постоянное
удержание всех bitmap и увеличение глобального кеша не добавлялись.

## Воспроизводимая методика

Стенд живёт вне checkout, в отдельном Android package `app.senreader.coldload`.
Он содержит две копии ReaderPage: состояние 367 перед этим этапом и исправление.
Одинаковый диагностический ImageProvider для обеих копий сохраняет прежний
ResizeImage и измеряет HTTP body, создание buffer/codec и `getNextFrame`.
Запись исходных сжатых файлов асинхронна и нужна только для сценария Б.
Это дополнительная нагрузка стенда, отсутствующая в production NetworkImage.

Каждый новый route получает отдельный локальный тестовый namespace библиотеки,
чтобы гарантировать старт с страницы 0. Прежние записи не удаляются.
Во всех прогонах выключен CPU sampling profiler; Timeline Dart/GC/Embedder
сохраняется потоком на ПК, дополненным хвостом кольцевого буфера.

1. **А: холодная сеть.** Закрыть тестовый reader, дождаться terminal completion
   прежних запросов, очистить только ImageCache отдельного тестового процесса,
   сменить generation ключей и игнорировать сохранённые сжатые файлы. Каждый
   cache miss действительно делает HTTP. Список страниц заранее получен через
   настоящий adapter. CDN, TLS/connection pool, OS/GPU caches не сбрасываются.
2. **Б: файл без decoded cache.** Новый route/generation, тот же изолированный
   ImageCache очищен, provider читает только захваченные оригинальные байты с
   диска; fallback в сеть запрещён. Это диагностический replay для отделения
   сети от decode; такого режима пока нет в основном приложении.
3. **В: прогретый повтор.** После Б вернуться к индексу 0 внутри того же route,
   сохранив ratios, streams и ImageCache, затем повторить тот же scroll.
   Во всех шести итоговых В-прогонах **0 новых загрузок/декодирований**.

Для каждой главы один порядок: А до/после, Б до → В до, Б после → В после.
Автоматическое перемещение — 4500 logical px за 6 с через штатный controller,
после появления route через 350 мс. Это контролируемая анимация, не имитация
ручного ввода и не финальное доказательство плавности пальцем. ADB swipe не
применялся. Разные моменты готовности/уточнения начальной геометрии могут дать
разное покрытие страниц даже при равном offset; номера/размеры записаны.

Измеряются build/raster FrameTimings p95/p99/max, over-budget и оценка missed
vsync, async network/decode/ready, появление RawImage в видимой геометрии,
heap/external memory, PSS, ImageCache и GC. `paintCandidate` — post-frame
наблюдение видимого RawImage, **не подтверждённый момент показа SurfaceFlinger**.
Время до него отсчитывается от `ColdLoad.RunOpen`, после подготовки namespace.
FrameTiming misses — оценка работы Flutter, не точное число отброшенных кадров.
Нулевые root/geometry counters внешнего агрегатора стенда не инструментированы
и не используются как результаты. Тяжёлые GPU/Perfetto polling не добавлялись.

Начальная серия с восстановленной позицией исключена целиком и сохранена в
`invalid-initial`. Глава 187 Senkuro и 220 ReadManga не найдены в доступных
списках; выбраны подтверждённые доступные главы. Ограничения доступа не обходились.

## Официальные основания

- [ImageCache](https://api.flutter.dev/flutter/painting/ImageCache-class.html):
  pending, LRU и live references имеют разную семантику; keepAlive bytes не
  равны памяти процесса.
- [precacheImage](https://api.flutter.dev/flutter/widgets/precacheImage.html):
  готовность первого кадра не гарантирует его дальнейшее удержание; pinning
  большого числа изображений несёт риск OOM. Увеличение кеша не выбрано.
- [ScrollAwareImageProvider](https://api.flutter.dev/flutter/widgets/ScrollAwareImageProvider/resolveStreamForKey.html):
  Image может отложить новый miss при быстром движении, но pending/cache hit
  используется сразу. Прямой resolve probe не проходит этот scroll-aware gate;
  он требует собственной ограниченной очереди.
- [Flutter performance best practices](https://docs.flutter.dev/perf/best-practices):
  сохраняются lazy list и локальные обновления; broad rewrite списка без
  подтверждённой причины не выполнялся.
